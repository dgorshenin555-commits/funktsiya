# Вариант Б: второй дизайн параллельно с текущим

**Дата:** 14 августа 2026
**Статус:** спецификация утверждается

## Задача

В Cloud Design создан новый дизайн платформы «Функция» — вариант Б. Его нужно
залить в тот же репозиторий, что и текущий вариант А, так чтобы:

- вариант А продолжал работать и оставался доступен по прежней ссылке;
- вариант Б разрабатывался параллельно и имел собственную публичную ссылку;
- к работе над обоими вариантами подключались другие люди — тем же способом,
  каким это уже происходит с вариантом А (доступ к репозиторию на GitHub).

## Исходные решения

Три развилки, закрытые до начала работ:

| Вопрос | Решение |
|---|---|
| Судьба вариантов | Б со временем заменит А; А должен жить, пока Б не готов |
| Публичное превью Б | Нужна отдельная ссылка, параллельно с А |
| Общая логика | Данные те же — Б это другая оболочка над той же моделью |

## Что такое вариант Б

Десктопный редизайн под кодовым названием *paper / ink / acid*: светлая
бумажная подложка, чёрный текст, кислотно-лаймовый акцент. Полностью
самодостаточен по стилям — в шапке `new_design.css` указано «Standalone, не
зависит от styles.css».

**Палитра:** `--paper #F1EFE9`, `--ink #14161A`, `--acid #C9F24A`,
плюс акценты `--signal #2440E8`, `--clay #DC5A2A`, `--moss #1F7A55`,
`--plum #6E3AD6`.
**Шрифты:** Unbounded (заголовки), Golos Text (текст), JetBrains Mono (цифры).
**Корневой класс:** `.nd` — обёртка всей оболочки.

Б покрывает все разделы А, то есть является полной заменой, а не частичным
макетом.

### Состав исходников

Лежат в `design-handoff-v2/` — 348 КБ JSX + 90 КБ CSS.

| Модуль | Экраны |
|---|---|
| `new_design.jsx` | `NewApp` — оболочка, Главная, Заявки |
| `new_design_wizard.jsx` | `OrderNew`, `ReqTrack` |
| `new_design_dirs.jsx` | `Pick`, `Cat` |
| `new_design_order.jsx` | `OrderCard`, `CompareOrder` |
| `new_design_detail.jsx` | `OrderDetail`, `ProProfile`, `Compare` |
| `new_design_more.jsx` | `Standards`, `Messages`, `Trust`, `Pricing`, `Settings` |
| `new_design_extra.jsx` | `Analytics`, `AiPick`, `Call` |
| `new_design_solo.jsx` | `SoloProfile` |
| `new_design_flow.jsx` | `OrderNewLite`, `Expertise` |
| `new_design_scrub.jsx` | `ScrubRail` |

Модули написаны как браузерные IIFE: используют глобальный `React` и
регистрируют экраны через `Object.assign(window, {...})`. Так работает превью в
Cloud Design. Для Next.js их нужно переобернуть в ES-модули с `'use client'` —
JSX-разметка переносится один в один, меняется только обвязка.

**Осторожно:** `OrderNew` объявлен дважды. В `new_design_flow.jsx` он
переименован в `OrderNewLite`, рабочая версия — в `new_design_wizard.jsx`.

## Архитектура решения

### Размещение

Вариант Б — обычный сегмент маршрута `app/v2/` в ветке `main`.

```
app/
├── layout.tsx          общий: <html><body><AppProvider>, БЕЗ globals.css
├── page.tsx            А: лендинг            + import globals.css
├── (internal)/         А: внутренние экраны  + import globals.css
├── auth/               А: вход               + import globals.css
└── v2/                 Б
    ├── layout.tsx      import ./v2.css, обёртка <div className="nd">
    ├── page.tsx        главная Б
    ├── orders/  experts/  manufacturers/  expertise/
    ├── standards/  chat/  analytics/  trust/  pricing/
    └── v2.css
```

Рассмотренные и отклонённые альтернативы:

- **Долгоживущая ветка `variant-b`.** Даёт изоляцию, которая не нужна (Б всё
  равно вливается в `main`), взамен требует постоянной ручной синхронизации
  `lib/` — а его активно правит второй разработчик. Плюс усложняет CI и
  провоцирует ошибки с базовой веткой при подключении новых людей.
- **Отдельный репозиторий.** Дублирует `lib/`, требует заводить доступы заново,
  превращает финальную замену А на Б в ручной перенос.

### Изоляция стилей

Главный технический риск: `app/globals.css` — 3362 строки полностью глобальных
правил (`:root`, `*`, `html`, `body`, плюс общие имена `.btn`, `.card`,
`.sidebar`). У Б свои значения тех же токенов. В одном документе они
конфликтуют.

Два барьера:

1. **Раздельные точки входа.** `globals.css` уходит из корневого layout в три
   файла варианта А. Next.js грузит CSS по дереву маршрута, поэтому в документе
   `/v2/` стилей А не будет, и наоборот. Файлы А при этом не перемещаются —
   правка в четыре строки.
2. **Scope-обёртка.** Токены Б переносятся из `:root` в `.nd` — этот класс уже
   есть в вёрстке Б как корневая обёртка. Даже при случайной совместной загрузке
   внутри `.nd` выигрывает Б по специфичности.

Следствие: переход между А и Б делается обычным `<a href>`, не `<Link>` —
клиентская навигация подтянула бы CSS обоих вариантов в один документ.

`brand-fonts.css` остаётся в корневом layout: шрифты общие.

### Общая логика

`lib/store.tsx`, `lib/mock-data.ts`, `lib/types.ts` — без изменений и без копий.
`AppProvider` в корневом layout обслуживает оба варианта. Новые поля для Б
добавляются в общие типы аддитивно, модель не форкается.

### Деплой

CI не меняется: `npm run build` собирает всё дерево `app/`, включая `v2/`.

| Вариант | Ссылка |
|---|---|
| А | `dgorshenin555-commits.github.io/funktsiya` |
| Б | `dgorshenin555-commits.github.io/funktsiya/v2` |

## Модель совместной работы

Оба варианта живут в одном репозитории, поэтому доступы не заводятся заново —
у участников уже есть право записи.

| | Вариант А | Вариант Б |
|---|---|---|
| Файлы | `app/page.tsx`, `app/(internal)/`, `app/auth/` | `app/v2/` |
| Ветки | `fix/…`, `feat/…` | `feat/v2-…` |
| PR в | `main` | `main` |

Правило: в чужую папку не лезем. Единственная общая территория — `lib/`,
изменения там анонсируются, потому что влияют на оба варианта сразу.

## Порядок работ

1. **Разобрать текущее состояние.** В рабочем дереве незакоммиченные правки
   «Функции 9»; ветка `fix/qa-round-2` от `sergeev81` на 9 коммитов впереди
   `main` и пересекается с ними в 6 файлах из 8. Развести до начала работ по Б.
2. **Развести CSS** — вынести `globals.css` из корневого layout в три точки
   входа А. Проверить, что А не изменился визуально.
3. **Каркас `app/v2/`** — маршруты по разделам, `v2.css`, обёртка `.nd`.
   На этом шаге появляется рабочая ссылка `/v2`.
4. **Перенос экранов** из `design-handoff-v2/` — по одному, каждый отдельной
   веткой `feat/v2-…`. Шаг распараллеливается на нескольких человек.
5. **Мерж в `main`** → автодеплой → две живые ссылки.
6. **Памятка команде** — дополнить `СОВМЕСТНАЯ-РАБОТА.md` разделом про два
   варианта.

Шаги 1–3 делаются последовательно одним человеком, шаг 4 — параллельно.

## Риски и проверка

Автотестов в проекте нет (`package.json`: только `dev`, `build`, `start`),
поэтому проверка — сборка плюс визуальный осмотр.

| Риск | Проверка |
|---|---|
| Вынос `globals.css` ломает вид А | Скриншоты `/`, `/orders`, `/auth` до и после |
| Б не попал в статический экспорт | После `next build` существует `out/v2/index.html` |
| Конфликты с веткой коллеги | Разбираются на шаге 1, до начала работ по Б |
| Перепутана версия `OrderNew` | Берётся из `new_design_wizard.jsx` |
